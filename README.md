# DBDenté — Phase 0 Demo

ระบบบริหารคลินิกทันตกรรม + Integrated Web DICOM Viewer (เดโมสำหรับ Customer Discovery)

**Flow หลักที่เดโมนี้พิสูจน์:** แตะซี่ฟันบน Tooth Chart → กรองฟิล์มของซี่นั้น → เปิดฟิล์มล่าสุดใน Viewer ทันที →
ปรับแสง / Invert / วัดความยาวราก (mm) → เทียบก่อน-หลังการรักษา 1x2 — บนเบราว์เซอร์และ iPad

```
apps/
  api/   Node.js (Express 5 + TypeScript) — Auth/RBAC, Audit Log, proxy ไป dcm4chee (DICOMweb)
  web/   Next.js 16 (App Router) + Tailwind 4 + Zustand + Cornerstone3D 5
```

## เริ่มใช้งาน

```bash
npm run setup     # ติดตั้ง dependency ทั้งหมด + สร้างข้อมูลเดโม
npm run dev       # API :4000 + Web :3000
```

เปิด http://localhost:3000 แล้วเลือกผู้ใช้ตามบทบาท (เดโมไม่มีรหัสผ่าน) เจ้าของคลินิกเข้ามาที่ **Dashboard** บทบาทอื่นเข้ามาที่ **คิววันนี้**

- **เคาน์เตอร์:**
  - เช็กอินคนไข้ที่มีนัด หรือรับ Walk-in → กด "เรียกเข้าห้อง" แล้วเลือกเก้าอี้ → เปิด **จอเรียกคิว** (`/display`) อีกแท็บ จะเห็นคิวขึ้นทันที
  - ลงทะเบียนคนไข้ใหม่ (ต้องถามประวัติแพ้ยาทุกครั้ง)
  - นัดหมายจากปฏิทิน: แตะช่องว่างเพื่อสร้างนัด ลากเพื่อย้ายนัด
  - **รับชำระ:** คิวที่ "รอชำระเงิน" กดปุ่ม `รับชำระ ฿…` → บิลดึงหัตถการให้แล้ว แก้ราคา/ส่วนลดได้ → แบ่งจ่ายเงินสด + โอน → ออกใบเสร็จ (พิมพ์หรือบันทึก PDF)
  - **ปิดยอด:** หน้ารับชำระ → "ปิดยอด" → นับเงินสดในลิ้นชัก ระบบคิดส่วนต่างให้ (ยอดไม่ตรงต้องใส่หมายเหตุ)
  - ไม่เห็นผังฟัน ฟิล์ม และ SOAP (RBAC)
- **ทันตแพทย์:** เปิดคนไข้ "สมชาย ใจดี" → แตะซี่ **36** → จะเห็น PA ก่อน/หลังรักษาราก → ติ๊ก 2 ภาพแล้วกด "เทียบ 1x2" → เขียน SOAP ด้วยเทมเพลต แล้วลงนาม
- **เจ้าของคลินิก:** ดูได้ทุกเมนู รวมถึง Audit Log และยกเลิกใบเสร็จได้ (ก่อนปิดยอด ระบบเปิดบิลใหม่ให้ออกแทน)
  - **Dashboard:** รายได้รายวัน / ตามหมอ / ตามหมวดหัตถการ, คนไข้ใหม่, อัตรามาตามนัด และสิ่งที่ต้องติดตาม (บิลค้าง, งานแล็บเลยกำหนด, วัสดุใกล้หมด)
  - **ค่ามือหมอ (DF):** ตั้ง % ตามหมวดหัตถการต่อหมอ และประกันรายได้ขั้นต่ำต่อวัน กด "ทดลองคำนวณ" ดูผลก่อนบันทึก และส่งออก CSV (เปิดใน Excel ได้)

**เอกสารยินยอม (E-Consent) บนแท็บเล็ต:**
1. เปิด `/kiosk` บนแท็บเล็ต (login ด้วยบัญชีพนักงานคนใดก็ได้) → เครื่องถูกล็อกไว้ที่หน้านี้
2. ที่เครื่องเคาน์เตอร์ เปิดแฟ้มคนไข้ → แท็บ "เอกสารยินยอม" → สร้างเอกสาร → "ส่งไปแท็บเล็ต"
3. คนไข้อ่าน ติ๊กยินยอม และเซ็นด้วยนิ้ว (เด็กให้ผู้ปกครองเซ็นแทนได้) → แฟ้มคนไข้อัปเดตทันที
4. ออกจากโหมด Kiosk: แตะรูปกุญแจมุมขวาบน แล้วใส่ PIN เดโม `2468`

ถ้ามีเครื่องเดียว กด "เซ็นบนเครื่องนี้" แทนการส่งไปแท็บเล็ตได้

**Phase 2–3 ที่ลองได้ในเดโม:**
- **ผ่อนชำระ / มัดจำ** (เคาน์เตอร์):
  - หน้า "ผ่อนชำระ / มัดจำ" แสดงงวดค้างและงวดที่ครบกำหนด กด "ออกบิลงวดนี้" แล้วรับชำระตามปกติ
  - รับมัดจำจากแท็บการเงินในแฟ้มคนไข้ แล้วใช้ "ตัดมัดจำ" ตอนรับชำระครั้งถัดไป
  - หน้ารับชำระรับบัตรเครดิต/เดบิตได้แล้ว
- **ค่ามือหมอ (DF):** ทันตแพทย์เห็นเฉพาะของตัวเอง (รายวันและรายเคส)
- **งานแล็บ:** บันทึกงานส่งแล็บและวันนัดรับ ระบบเตือนงานเลยกำหนด/ใกล้ครบกำหนด และผูกค่าแล็บกับรายการในบิลเพื่อหักก่อนคิด DF
- **สต็อกวัสดุ** (ผู้ช่วย/เจ้าของ):
  - รับเข้าเป็นล็อตพร้อมวันหมดอายุ และเบิกแบบหมดอายุก่อนใช้ก่อน
  - ตัดสต็อกอัตโนมัติตามหัตถการเมื่อรับชำระ และคืนสต็อกเมื่อยกเลิกใบเสร็จ
  - เตือนเมื่อต่ำกว่าจุดสั่งซื้อ หรือใกล้หมดอายุ
- **Local Bridge** (ผู้ช่วย/เจ้าของ):
  - สถานะเครื่อง X-ray ที่เชื่อมอยู่
  - จับคู่ไฟล์ที่อ่าน HN ไม่ได้กับคนไข้ และสั่งส่งไฟล์ที่ล้มเหลวซ้ำ
  - จำลองเครื่องด้วย `npm run bridge:sim` (ใน `apps/api`) เครื่องจะขึ้นออนไลน์ และไฟล์ที่จับคู่แล้วจะถูกส่ง (จำลอง ไม่ได้ส่งเข้า PACS จริง)

ข้อมูลคิวและนัดของวันนี้สร้างโดยอิงเวลาที่รัน `npm run seed` เปิดเดโมวันอื่นให้รัน seed ใหม่ก่อน seed ยังสร้างประวัติย้อนหลัง 60 วัน (visit, ใบเสร็จ, ปิดยอด) ให้ Dashboard และ DF มีตัวเลข ข้อมูลทั้งหมดเป็นข้อมูลสมมติ

**Real-time:** คิว นัด และสถานะเก้าอี้อัปเดตทุกเครื่องผ่าน Socket.io
- ต้องมี JWT ถึงจะเชื่อมต่อได้ และแยกห้องตามคลินิก
- server ส่งแค่สัญญาณ แล้วแต่ละหน้าจอดึงข้อมูลผ่าน API ตามสิทธิ์ของตัวเอง
- จอเรียกคิวได้เฉพาะเลขคิว ห้อง และชื่อแบบย่อ (PDPA)
- บิล/ปิดยอด และเอกสารยินยอมก็อัปเดตแบบเดียวกัน การส่งเอกสารไปแท็บเล็ตส่งแค่ id แท็บเล็ตดึงเนื้อหาผ่าน API เอง

**เปิดจาก iPad:** ให้ iPad อยู่ใน Wi-Fi เดียวกัน แล้วเปิด `http://<IP เครื่อง>:3000` ได้เลย
เว็บจะเรียก API ที่ hostname เดียวกัน พอร์ต 4000 ให้เอง

ไฟล์ DICOM ตัวอย่างสำหรับทดสอบปุ่มอัปโหลดอยู่ที่ `apps/api/data/samples/`
ภาพทั้งหมดเป็นภาพสังเคราะห์และคนไข้เป็นข้อมูลสมมติ

## dcm4chee ทดสอบในเครื่อง (Docker)

```bash
cd infra/dcm4chee-dev && docker compose up -d     # UI: http://localhost:8080/dcm4chee-arc/ui2
```

ไม่เปิด security และเปิดพอร์ตเฉพาะ localhost จึงใช้กับข้อมูลทดสอบเท่านั้น

ใส่ภาพเดโมเข้าไปครั้งแรกด้วย `DCM4CHEE_READ_ONLY=false npm run seed` (รันใน `apps/api`)
ลบทิ้งทั้งหมดด้วย `docker compose down -v`

## เชื่อมต่อ dcm4chee

ตรวจการเชื่อมต่อแบบอ่านอย่างเดียว (ไม่พิมพ์ชื่อคนไข้):

```bash
cd apps/api
npm run pacs:check                                        # auth + QIDO
npm run pacs:check -- --patient <PatientID>               # + WADO/thumbnail พร้อมจับเวลา
npm run pacs:check -- --patient <PatientID> --link p1     # ผูกคนไข้เดโม p1 กับ PatientID ที่มีใน PACS
```

`DCM4CHEE_READ_ONLY=true` เป็นค่าเริ่มต้น ระหว่างนี้ API จะไม่อัปโหลด, seed จะไม่ส่งภาพ และเว็บจะซ่อนปุ่มอัปโหลด

แก้ไฟล์ `apps/api/.env`:

```ini
IMAGE_SOURCE=dcm4chee
DCM4CHEE_RS_URL=http://<host>:8080/dcm4chee-arc/aets/<AET>/rs
# ถ้าเปิด security: ใช้ DCM4CHEE_TOKEN หรือ DCM4CHEE_KC_* (client credentials)
```

จากนั้นรัน `npm run seed` เพื่อส่งภาพเดโมเข้า dcm4chee ผ่าน STOW-RS แล้วรัน `npm run dev`

| การทำงาน | DICOMweb ที่ใช้ |
|---|---|
| รายการฟิล์มของคนไข้ | QIDO-RS `/instances?PatientID=` |
| เปิดภาพใน Viewer | WADO-URI `/wado?requestType=WADO&contentType=application/dicom&transferSyntax=*` |
| Thumbnail | WADO-RS `/rendered` (ถ้าใช้ไม่ได้จะ render จากไฟล์เอง) |
| อัปโหลด | STOW-RS `/studies` |

หลักการด้านความปลอดภัย:
- **ห้ามเปิด dcm4chee สู่ภายนอก** Browser คุยกับ API เท่านั้น และ API จะตรวจ JWT, บทบาท และ `clinic_id` ทุกคำขอ
- **PatientID รูปแบบ `{clinic_code}-{HN}`** และ IssuerOfPatientID = clinic code กัน HN ชนกันข้ามคลินิก ตอนอัปโหลด API เขียนทับค่าเหล่านี้ให้เอง
- **ตรวจว่า SOP Instance เป็นของคนไข้รายนั้นจริง** ก่อนส่งไฟล์ (กันการเดา UID) และปฏิเสธการอัปโหลด UID ซ้ำที่เป็นของคนไข้อื่น
- **Audit Log:** เปิดดูประวัติ / เปิดดูฟิล์ม / อัปโหลด / แก้ไขผังฟัน / ผูกฟิล์ม / รับชำระ / ยกเลิกใบเสร็จ / ปิดยอด / สร้าง-เซ็น-เปิดดูเอกสารยินยอม / ปลดล็อก Kiosk / ดูและตั้งกฎ DF / แผนผ่อน / งานแล็บ / เคลื่อนไหวสต็อก / จับคู่ไฟล์ Bridge
- **Local Bridge ยืนยันตัวด้วย token ประจำเครื่อง** (เก็บเป็น SHA-256, ไม่ใช้ JWT ของผู้ใช้) และได้รับแค่ PatientID ของไฟล์ที่เจ้าหน้าที่จับคู่แล้ว

หลักการด้านการเงินและเอกสารยินยอม:
- **จำนวนเงินเก็บเป็นสตางค์ (จำนวนเต็ม)** กันปัญหาทศนิยม · ยอดชำระต้องเท่ากับยอดบิลพอดี
- **ใบเสร็จไม่ถูกลบ** ยกเลิกได้เฉพาะเจ้าของ ต้องระบุเหตุผล และทำไม่ได้หลังปิดยอด · ทันตแพทย์/ผู้ช่วยไม่เห็นยอดเงิน
- **ปิด visit ผ่านการรับชำระเท่านั้น** (รอชำระเงิน → เสร็จแล้ว)
- **เอกสารยินยอมเก็บข้อความทั้งชุดตอนสร้าง** แก้เทมเพลตภายหลังไม่กระทบฉบับที่เซ็นแล้ว · เซ็นแล้วแก้ไม่ได้ และเก็บ SHA-256 ของเนื้อหา + การติ๊ก + ลายเซ็น + เวลา ไว้ตรวจว่าไม่ถูกแก้
- **PIN ออกจาก Kiosk** ตรวจที่ API และล็อก 5 นาทีเมื่อผิด 5 ครั้ง

## สิ่งที่ตั้งใจยังไม่ทำในระยะ 0

- **ข้อมูล:** เก็บเป็น JSON file (`apps/api/data/db.json`) ระยะ 1 จะย้ายไป PostgreSQL + Prisma
- **Login:** ยังเป็นการเลือกผู้ใช้ ยังไม่มีรหัสผ่าน / MFA
- **การวัดบนฟิล์ม:** ยังไม่บันทึกลงฐานข้อมูล (Dicom_Annotations)
- **อัปโหลด:** รับเฉพาะไฟล์ `.dcm` (JPG/TIFF → DICOM Secondary Capture จะทำใน Local Bridge)
- **การเงิน:** ใบเสร็จยังไม่ใช่ใบกำกับภาษี · รายการราคา วัสดุต่อหัตถการ และรายชื่อแล็บยังแก้ในหน้าตั้งค่าไม่ได้ (อยู่ใน seed) · บัตรเครดิตบันทึกยอดอย่างเดียว ยังไม่เชื่อมเครื่อง EDC
- **DF:** คิดจากวันที่รับชำระ · ค่าวัสดุเป็นค่าคงที่ต่อหัตถการ · ยังไม่มีการอนุมัติ/ปิดงวดจ่าย DF
- **Local Bridge:** ฝั่งเว็บและ API พร้อมแล้ว ตัวโปรแกรม Bridge จริงที่ติดตั้งในคลินิกยังไม่ได้สร้าง (มีเฉพาะตัวจำลอง)
- **ตั้งค่าคลินิก:** ยังเป็นหน้า "อยู่ในแผน"
- **E-Consent:** PDF ใช้การพิมพ์ของเบราว์เซอร์ · ข้อความในเทมเพลตเป็นตัวอย่าง ใช้จริงต้องให้ที่ปรึกษากฎหมายตรวจ · การล็อก Kiosk ทำที่หน้าเว็บ (ควรใช้ร่วมกับ Guided Access บน iPad / Screen pinning บน Android) · ยังถอนความยินยอมที่ไม่บังคับ (เช่น LINE) ผ่านระบบไม่ได้
- **ยังไม่มี:** แผนการรักษา/ใบเสนอราคา
- **บัตรประชาชน:** ปุ่มอ่านบัตรรอ Local Bridge (Phase 2) ตอนนี้กรอกเลขเองได้ ระบบตรวจ checksum ให้
- **ปฏิทิน:** มีมุมมองรายวัน (ตามเก้าอี้ / ตามหมอ) ยังไม่มีมุมมองสัปดาห์และตารางเวรหมอ
- **ค่าระยะที่วัดได้ขึ้น "Proj":** Cornerstone คำนวณจาก Imager Pixel Spacing (ที่ระดับเซนเซอร์ ยังไม่ชดเชยการขยายภาพ) ซึ่งเป็นพฤติกรรมปกติของภาพ X-ray แบบฉาย
